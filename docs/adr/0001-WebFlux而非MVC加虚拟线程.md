# ADR 0001：WebFlux 而非 MVC + 虚拟线程

- 状态：已采纳
- 日期：2026-10

## 背景

AgentFlow 的核心负载是万级 SSE 长连接 + 逐 token 流式转发 + 上游模型限流后的慢响应。MVC 的一连接一线程模型在 1 万连接下需要 1 万个平台线程（默认栈 1MB，光栈就 10GB），且 Tomcat 每个慢请求都独占线程，慢模型会把线程池拖垮。虚拟线程（JDK 21 才正式可用，本项目锁 Java 17）能解决阻塞式并发的线程数问题，但流式场景的背压、取消传播、有界缓冲并不是线程模型问题。

## 决策

全栈采用 Spring WebFlux（Netty 事件循环）+ Reactor：

- 连接数与线程数解耦，事件循环线程固定少量；
- 背压沿操作符链从 SSE 客户端一路上溯到模型流式读取；
- 取消信号（`doOnCancel`）沿链层级联，统一回收模型连接、舱壁信号量与配额预扣；
- 阻塞调用（MyBatis/JDBC）显式调度到 boundedElastic，禁止侵入事件循环。

## 备选方案

1. **MVC + 虚拟线程**：被否。虚拟线程让阻塞代码能开很多线程，但 SSE 场景需要的是"对反压与取消的一等表达"，阻塞式写法里背压只能靠手工队列与轮询模拟，取消传播要自行贯穿每一层；且 Java 17 没有正式虚拟线程，依赖孵化器特性不可接受。
2. **MVC + Servlet 3.1 异步 / DeferredResult**：被否。异步只是释放容器线程，业务侧仍是回调地狱，无背压协议，慢客户端缓冲仍需自建。
3. **原生 Netty 手写**：被否。控制力最强但开发成本过高，且失去 Spring 生态（校验、Actuator、Micrometer）。

## 代价

- **调试难**：异步栈不连续，异常堆栈跨调度器断裂，排障必须靠 Reactor 调试代理与 traceId 贯穿日志；
- **阻塞库不兼容**：MyBatis、JDBC 等阻塞调用一旦误入事件循环线程，不会报错而是静默拖垮全部连接，必须靠架构约束（ArchUnit 规则）与代码评审防守；
- **团队学习成本**：Reactor 操作符语义（`flatMap` 并发度、`publishOn`/`subscribeOn` 差异、背压请求量）有学习曲线，新人上手期约 1~2 周；
- **生态约束**：选型同时排除了 Spring MVC 体系内的若干惯用方案（如 Servlet Filter 链），鉴权等横切逻辑需以 WebFilter 重写。

## 验证

- 1 万 SSE 连接压测（`loadtest/sse_10k.js`）下 Netty 事件循环线程数恒定（CPU 核数 ×2），连接从 1 千加到 1 万 CPU 仅从 12% 升到 19%（见 `docs/BENCHMARK.md` S3）；
- 背压场景（`loadtest/backpressure.js`）上游 500 tps 快吐、200 个慢读连接，实例无 OOM，丢帧计数可见；
- ArchUnit 规则持续守护"事件循环线程不做阻塞调用"的边界。

## 结论

流式 + 背压 + 取消传播是 Reactor 的原生优势，Netty 侧本就异步；WebFlux 是该项目负载形态下的正确默认。代价通过 ArchUnit 规则、统一调度封装（阻塞调用收口）与文档（`docs/CONCURRENCY.md` 线程模型一节）收敛。
