# ADR 0003：TPM 预扣结算

- 状态：已采纳
- 日期：2026-10

## 背景

供应商按 TPM（tokens per minute）限流与计费，但请求发出前无法知道响应会消耗多少 token：若按请求数（RPM）限流，一个 8000 token 的大请求顶 100 个小请求，供应商侧照样超限；若等响应结束再扣减，则并发高峰期大量请求同时通过检查，瞬时严重超发，触发供应商 429 甚至封禁。

## 决策

采用"预扣-结算"两阶段配额：

1. **预扣**（`quota_reserve.lua`）：请求前按 `prompt 估算 tokens + maxTokens` 从 Redis 令牌桶原子扣减；不足则直接返回 `-32005`（429）。
2. **结算**（`quota_settle.lua`）：响应结束拿到真实 usage，在 `doFinally` 中把"预扣 - 实际"退回桶中。

Lua 保证"读-判断-扣减"原子；时间取 Redis `TIME` 命令，避免多实例时钟漂移导致补充速率算错；外层叠加本地令牌桶预检（容量 = 全局/实例数 × 1.2），Redis 不可用时降级为本地近似限流。

## 备选方案

1. **只按 RPM 限流**：被否。请求大小方差极大，供应商按 token 计费，RPM 限流既不安全也不经济。
2. **响应后记账**：被否。检查与扣减不同时发生，并发下必超发。
3. **按历史平均输出长度预估**：被否。均值预估在长尾（报告生成类）偏差大，不如按 `maxTokens` 上限保守。
4. **单机内存桶**：被否。多实例部署下各实例独立计数，全局额度无法保证。

## 代价

- **估算偏差导致短时超发或保守**：按 `maxTokens` 上限预扣，输出短时配额被多占、吞吐偏保守；若 prompt 估算偏低且模型输出顶满，则结算前处于"临界超发"状态。偏差被上限约束，不会无限放大；
- **两次 Redis 往返**：每次调用多一次结算 RTT（Lua 单次 < 1ms，可接受）；
- **漏结算风险**：取消、异常、实例崩溃都可能跳过结算，因此结算必须挂在 `doFinally`；此外预扣记录（`TokenReservation`）带过期兜底，长时间未结算的预留由对账任务回收。

## 验证

- `loadtest/quota_burst.js` 以 400/s 突发（rpm=600）压测：429 占比 38.2%，无超发；突发结束 60 秒内桶余量回正（见 `docs/BENCHMARK.md` S4）；
- 集成测试覆盖"预扣打满返回 `-32005`"与"结算后额度回正"两条路径；
- Redis 故障演练：停止 Redis 后限流自动降级为本地近似（`LocalRateLimiter`），服务不整体失败，恢复后自动回到精确限流。

## 结论

预扣-结算是"请求前不知道 token 数"这一约束下兼顾不超发与可用性的标准解法。偏差是可控的、方向是保守的；配套 `doFinally` 强制结算与预留过期兜底，把漏结算的窗口压到最小。
