# ADR 0004：滑窗 + 摘要压缩

- 状态：已采纳
- 日期：2026-10

## 背景

多轮会话历史会随轮次线性增长，而模型上下文窗口有限（mock-large 32k）。完全不裁剪迟早超窗报错；简单粗暴按条数截断也不可行——一条工具返回可能 5000 token，按条数裁会爆窗。需要一种按 token 计量、对任务连续性损伤最小的裁剪策略。

## 决策

两级裁剪（`ContextBuilder` + `ContextCompressor`）：

1. **整轮滑窗**：按 token 预算（history 区段占 45%）从最老轮次开始整轮剔除，保留最近若干完整轮次，保证上下文里的对话轮次边界完整；
2. **摘要压缩**：整轮裁完仍超过预算 90%（`compressor-trigger-ratio`）时，把被裁掉的历史压缩成一段不超过 500 token 的摘要（`summary-max-tokens`），以系统消息形式放回上下文头部；
3. **关键事实结构化兜底**：计划、工具结果等关键事实不落自然语言，落 `state_json` 结构化字段，续跑与构造上下文时直接引用，不依赖摘要保真。

## 备选方案

1. **不裁剪，超窗即报错**：被否。长会话必然撞窗，体验不可接受。
2. **按消息条数截断**：被否。条数与 token 无稳定关系，单条大消息即可撑爆窗口。
3. **全量历史每次重摘要**：被否。每轮都付一次全量摘要的成本与延迟，且摘要漂移累积失真。
4. **向量召回替代滑窗**：被否（作为补充而非替代）。pgvector 长期记忆（`VectorMemory`）负责"很久以前的相关事实"，滑窗负责"最近对话的连续性"，两者互补；纯召回会丢失对话的局部连贯。

## 代价

- **摘要丢细节**：500 token 的摘要不可能保留全部细节，被裁历史中的具体数字、ID 可能丢失——这是接受的取舍，关键事实走结构化字段兜底；
- **多一次模型调用**：触发压缩时多一次摘要请求，增加延迟与 token 成本（摘要限 500 token，成本可控）；
- **实现复杂度**：要维护"轮次边界 + token 计量 + 触发比例"三件套，比一行截断复杂得多。

## 验证

- `ContextBuilderTest` 覆盖：按 token 计量裁剪、整轮边界保持、预算四区段（system/tools/history/output）分配；
- 超长会话演练：构造历史占用超预算 90% 的会话，确认触发压缩且摘要 ≤ 500 token，上下文不超长报错而是平滑降级；
- 多轮压测（`loadtest/agent_multi_turn.js`）端到端 P95 4.87s，含工具调用与上下文组装开销，证明裁剪路径不是延迟热点。

## 结论

滑窗保连续性、摘要保大意、结构化字段保关键事实，三层组合在 token 预算内取得可接受的上下文质量。摘要丢细节是明确接受的代价，并用结构化状态消解其影响。
