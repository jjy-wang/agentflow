# ADR 0005：状态机 + 租约

- 状态：已采纳
- 日期：2026-10

## 背景

一次 Agent run 执行几十秒到两分钟，期间实例可能发版、宕机、被 kill。若执行状态只在内存中，实例挂掉即任务丢失；若用"请求-连接"绑定（连接断任务亡），客户端任何网络抖动都浪费已消耗的 token。多实例部署还要求：任务可以被任意健康实例接管，且绝不能被两个实例同时执行。

## 决策

run 状态全量落 PG，实例通过租约声明所有权：

- **状态机**：`PENDING → RUNNING → (WAITING_APPROVAL) → SUCCEEDED / FAILED / CANCELED / TIMEOUT`，所有迁移走条件更新（`UPDATE ... WHERE state=?`），非法迁移被数据库层拒绝；
- **执行现场**：`state_json` 持久化当前步骤、计划、已执行工具、累计 token，支持断点续跑；
- **租约**：执行实例持有 60 秒租约（`lease-seconds`）并周期续期；`RunRecoveryJob` 每 5 秒扫描，用 `SELECT ... FOR UPDATE SKIP LOCKED` 抢占租约到期的 run，批量 50；
- **幂等**：工具执行以 `(run_id, tool_call_id)` 唯一约束 `ON CONFLICT DO NOTHING`，续跑重放不会重复执行；LLM 调用不可续传，只能整步重发，单步成本受 `maxTokens` 约束。

## 备选方案

1. **内存状态 + 连接绑定**：被否。实例挂 = 任务丢，无法多实例。
2. **消息队列重投**：被否。Agent run 是长耗时流式任务，MQ 可见性超时与重复消费语义不匹配；且缺乏"执行到哪一步"的现场。
3. **分布式锁（Redis SETNX）全程持有**：被否。锁挂了无法区分"持有者优先死"与"持有者优先慢"，且无执行现场，恢复后仍要从零开始。
4. **K8s Job 级重试**：被否。引入 K8s 超出技术栈边界，且粒度太粗。

## 代价

- **复杂度上升**：状态机迁移表、租约续期、恢复任务、`state_json` 版本兼容，每个都是新增的故障面；
- **必须配套幂等**：续跑会整步重发 LLM 调用、重放工具调用，没有 `(run_id, tool_call_id)` 唯一约束就会重复扣库存式的副作用；幂等约束本身也带来"首次成功但响应丢失"时的返回一致性问题（当前策略：冲突时返回首次记录的结果）；
- **恢复延迟**：故障 run 最长要等租约过期（60s）+ 扫描周期（5s）才被接管，不适合秒级恢复要求的场景。

## 验证

- 故障演练：run 执行中 `docker compose stop app1`，app2 在 60 秒租约过期 + 5 秒扫描周期内接管并从断点续跑；
- 幂等验证：同一 `(run_id, tool_call_id)` 重放，`tool_invocation` 表无重复行（唯一约束 + `ON CONFLICT DO NOTHING`）；
- 双跑防护验证：`SKIP LOCKED` + 条件更新，两个实例竞争同一 run 时受影响行数为 0 的一方放弃，审计链中无双执行记录；
- 告警 5（恢复积压）长期静默，证明恢复链路稳定（见 `docs/RUNBOOK.md`）。

## 结论

状态机 + 租约 + `SKIP LOCKED` 是"多实例抢占、断点续跑、绝不双跑"三约束下不引入新中间件的最简方案。复杂度与幂等要求是该方案的固有成本，已通过唯一约束、条件更新与恢复任务成对落地。
